# แจ้งเตือน LINE ไม่ออกเลยสักข้อความ — ไล่แก้ตามนี้

อาการที่เจอ (3 ก.ย. 2026): ส่งใบแจ้งซ่อมแล้วผู้จัดการโรงงานไม่ได้ลิงก์อนุมัติ, อนุมัติแล้วผู้แจ้งซ่อม
และผู้จัดการทั่วไปก็ไม่ได้รับ — และหน้าตั้งค่า > **ส่งข้อความทดสอบจริง** ขึ้นว่า
`❌ ไม่ถึงใครเลย — relay ไม่พบผู้รับสำหรับการแจ้งเตือนนี้` ทั้งที่ตาราง **ผู้รับแจ้งเตือนที่แอปหาเจอตอนนี้**
บอกว่าบทบาทนั้นมีผู้รับ 2 คน

## ทำไมข้อความเดิมถึงพาไปแก้ผิดจุด

ข้อความ "relay ไม่พบผู้รับ" เป็นคำ **เดา** ของแอปเอง ไม่ใช่คำตอบจริงของ relay: โค้ดเดิมเห็นแค่
`sent = 0` แล้วสรุปเหมารวมว่าไม่มีผู้รับ ทั้งที่ `sent = 0` เกิดได้จากอย่างน้อย 4 สาเหตุที่ต้องแก้คนละที่

| สาเหตุจริง | ต้องไปแก้ที่ |
|---|---|
| โค้ดใน Apps Script เป็นเวอร์ชันเก่า (ไม่อ่านฟิลด์ `userIds` ที่แอปส่งไปให้) | Apps Script → วางโค้ดใหม่ → Deploy |
| `LINE_CHANNEL_ACCESS_TOKEN` ผิด/หมดอายุ (LINE ตอบ 401) | Script properties |
| `userId` ของผู้รับผิด หรือเจ้าตัวยังไม่ได้เพิ่ม OA เป็นเพื่อน / บล็อกไว้ (LINE ตอบ 400) | หัวข้อคำขอสิทธิ์ในแอป |
| ส่งครบโควตาข้อความของเดือน (LINE ตอบ 429) | LINE OA Manager |
| ไม่มีผู้รับจริงๆ | ผูก LINE ในแอป / แท็บ `แจ้งเตือน LINE - ผู้รับ` |

ตั้งแต่ `APP_VERSION 2026-09-03.1` แอปจะไม่เดาแล้ว: relay ส่ง `version`, `targets`, และ `errors`
(รหัสตอบกลับจริงของ LINE) กลับมาทุกครั้ง แล้วแอปแสดงเป็นลูกโซ่ให้เห็นว่าขาดตอนที่ขั้นไหน

> แอปหาผู้รับได้ 2 คน → relay หาได้ 2 คน → LINE รับไป 0 ข้อความ · relay v2026-09-03.1

## ขั้นตอนแก้ (ทำตามลำดับ)

### 1. อัปเดตโค้ด relay ให้ตรงกับแอป ← ทำข้อนี้ก่อนเสมอ

ไฟล์ `docs/line-relay.gs` ใน repo **ไม่ได้รันเอง** เป็นแค่ต้นฉบับสำหรับคัดลอกไปวาง โค้ดที่ทำงานจริง
อยู่ในเอดิเตอร์ของ Apps Script เท่านั้น แก้ไฟล์ใน repo แล้วไม่ไป Deploy = ระบบยังใช้โค้ดเก่าอยู่

1. เปิด Apps Script โปรเจกต์ **LineOA MT**
2. เปิดไฟล์ `Code.gs` → เลือกทั้งหมด → วางเนื้อหาของ `docs/line-relay.gs` ทับทั้งไฟล์
3. **Deploy → Manage deployments → ✏️ (แก้ไข) → Version: `New version` → Deploy**
   (ต้องเป็น *New version* เท่านั้น ถ้าไม่เลือก URL เดิมจะยังเสิร์ฟโค้ดเก่า)
4. กลับมาที่แอป → หน้าตั้งค่า → **ทดสอบ relay ตอนนี้** ต้องขึ้น
   `✅ โค้ด relay เป็นเวอร์ชันล่าสุด (2026-09-03.1)`

### 2. กด "ส่งข้อความทดสอบจริง" แล้วอ่านบรรทัดลูกโซ่

* **แอปหาผู้รับได้ 0 คน** → ยังไม่มีใครถูกผูก LINE ไว้กับบทบาทนั้น: ไปที่ **คำขอสิทธิ์เข้าใช้งาน**
  แล้วเลือก LINE ให้ผู้ใช้แต่ละคน หรือเพิ่มแถว (บทบาท, userId) ในแท็บ `แจ้งเตือน LINE - ผู้รับ`
* **relay หาได้ 0 คน ทั้งที่แอปหาได้ > 0** → โค้ด relay ยังเป็นเวอร์ชันเก่า กลับไปทำข้อ 1 ให้ครบ
* **LINE รับไป 0 ข้อความ ทั้งที่ relay หาได้ > 0** → อ่านรหัส HTTP ที่แอปแสดงต่อท้าย:
  * `401` → token ผิด/หมดอายุ ออกใหม่ที่ developers.line.biz → Messaging API → Channel access token
    แล้ววางที่ Apps Script → Project Settings → Script properties (`LINE_CHANNEL_ACCESS_TOKEN`)
  * `400` → `userId` ผิด หรือเจ้าตัวยังไม่ได้เพิ่ม OA เป็นเพื่อน — ให้เจ้าตัวทักหา OA หนึ่งครั้ง
    แล้วเอา userId จากแท็บ `LINE Users` มาผูกให้ในแอป
  * `403` → token เป็นของคนละ channel กับ OA ที่ผู้รับเป็นเพื่อนอยู่
  * `429` → โควตาข้อความของเดือนหมด

### 3. ตรวจว่าครบทุกบทบาทที่ต้องได้รับ

ตาราง **ผู้รับแจ้งเตือนที่แอปหาเจอตอนนี้** ต้องไม่มีบทบาทไหนเป็น 0 — โดยเฉพาะ
`fm` (อนุมัติ 1), `gm` (อนุมัติ 2), `maint` (มอบหมายช่าง)
ส่วนผู้แจ้งซ่อมและช่างเป็นการส่ง "เจาะจงคน" จึงต้องผูก LINE รายคนในหัวข้อคำขอสิทธิ์

## ✅ สาเหตุจริงที่ยืนยันแล้ว (4 ก.ย. 2026) — อ่านก่อนไล่หัวข้ออื่น

อาการ "แจ้งเตือนถึงแค่บางคน" รอบนี้เกิดจาก **สามเรื่องที่ไม่เกี่ยวกันเลย** ทับกันอยู่ ไม่ใช่เรื่องเดียว
และไม่มีเรื่องไหนเป็นเรื่อง "ผูก LINE ไม่ครบ" — ตอนตรวจ คำขอสิทธิ์ 27 รายการอนุมัติครบและมี
`lineUserId` ครบทุกคน

### 1. token ของ relay ส่งไม่ออกเลยสักข้อความ (31 ส.ค. – 3 ก.ย.)

แท็บ **`Relay Log`** มีแถว `push` 56 แถว **เป็น HTTP 401 ทั้งหมด** ข้อความเดียวกันหมด:

```
HTTP 401 → U82dbdaf5... : {"message":"Authorization header required.
                            Must follow the scheme, 'Authorization: Bearer <ACCESS TOKEN>'"}
```

ข้อความนี้ **ไม่ใช่** "token หมดอายุ" (อันนั้น LINE ตอบ `Invalid access token`) แต่แปลว่า LINE
แกะ header เป็น bearer token ไม่ได้ — ค่าใน Script property มีตัวอักษรอยู่ (จึงผ่าน guard
`if(!token)` ใน `pushTo_` ไปยิงจริง) แต่ไม่ใช่ token เปล่าๆ สาเหตุที่พบบ่อยสามอย่าง:

1. วางทั้ง `Bearer xxxxx` ลงไป → header กลายเป็น `Bearer Bearer xxxxx`
2. คัดลอกมาแล้วติดขึ้นบรรทัดใหม่/ช่องว่างกลางสตริง (`cfg_()` trim แค่หัวท้าย ตัวกลางรอด)
3. คัดลอกมาไม่ครบ (long-lived token ยาว 172 ตัว)

> **บทเรียน:** อย่าเดาสาเหตุจากฝั่งแอป — เปิดแท็บ `Relay Log` ก่อนเสมอ มันบอกรหัสตอบกลับจริง
> ของ LINE เป็นรายคน และ `?key=selftest` → `checks.accessToken` ยืนยันได้ใน 10 วินาที

### 2. ตัวบันทึกการแจ้งเตือนหายเองจาก race (แก้แล้วใน APP_VERSION 2026-09-04.1)

คีย์ `notifications` เป็นอาร์เรย์ก้อนเดียว เขียนทีไรทับทั้งก้อน โค้ดเดิมยิง
`storeSet('notifications', state.notifications)` จากอาร์เรย์ในหน่วยความจำตรงๆ ถึง 3 จุด
(`pushNotification`, `markAllRead`, และ **`openDetail` ซึ่งยิงทุกครั้งที่มีคนเปิดใบ**) จึงหายได้สองทาง:

* สองเครื่องกดพร้อมกัน → คนเขียนทีหลังทับของคนแรก
* `pushNotification()` ค้างรอ LINE หลายวินาที ระหว่างนั้น `pollForUpdates()` (ทุก ~3 วิ) อ่านค่าเก่า
  มาทับ `state.notifications` แถวที่เพิ่งเพิ่มหลุดจากหน่วยความจำ แล้วการเขียนครั้งถัดไปเอา
  อาร์เรย์ที่ขาดไปทับลงชีตถาวร

หลักฐานในชีต: `ST-WH005/26` มีแถว fm/gm แต่ **หาย requester ×3 และ maint ×1** ทั้งที่
`statusHistory` เดินครบทุกขั้น · `GR063/26` หายแถว fm ตอนสร้างใบ · `GR062/26` หาย requester + maint

แก้โดยให้ทุกการเขียนผ่าน `saveNotifications()` ซึ่งดึงของล่าสุดมาเป็นฐานก่อนเสมอ (แบบเดียวกับ
`saveAccessRequests()`) และเก็บแถวที่เครื่องนี้เพิ่งสร้างไว้ใน `pendingNotifs` จนกว่าจะเห็นมัน
กลับมาจากเซิร์ฟเวอร์จริง — รอบ poll จึงลบของที่ยังไม่ยืนยันทิ้งไม่ได้อีก

### 3. ช่างไม่เคยมีแจ้งเตือนในแอปเลย (แก้แล้ว)

ไม่มี `pushNotification('tech', …)` อยู่ในโค้ดสักที่ ช่างได้ผ่าน LINE ทางเดียว แท็บ `การแจ้งเตือน`
ทั้งชีตจึงมี fm 45 · gm 28 · maint 30 · requester 66 · **tech 0** ตั้งแต่เปิดระบบมา พอ token พัง
ช่างจึงไม่เหลืออะไรเลย ตอนนี้ใช้ `notifyTech()` ซึ่งลงทั้งกระดิ่งในแอปและ LINE

พ่วงอีกจุด: `notifIsMine()` เทียบชื่อกับ `state.myName` อย่างเดียว แต่ช่างถูกอ้างด้วย "ชื่อช่าง"
(`ศักดา  สนผา (ผช.ผจก.แผนกวิศวกรรม)`) ซึ่งไม่ตรงกับชื่อในคำขอสิทธิ์ (`ศักดา สนผา`) จึงเพิ่มการเทียบ
กับ `state.techIdentities` ด้วย

### 3.1 ช่างที่ยังไม่มี LINE — ไม่ยิงเลย โดยตั้งใจ

ช่าง 3 คนในแท็บ `ช่าง` ยังไม่มี `userId` ผูกไว้: **ศิลป์ทวี  พรหมพิลา**, **ไกรทอง  มีผักไหม**,
**ช่างฐิติวัชร์ (ทั่วไป)**

สามคนนี้ **ล็อกอินเข้าแอปไม่ได้ด้วย** — ไม่มีแถวใน `accessRequests` และ `userId` ในแท็บ
`สิทธิ์ผู้ใช้ LINE` ก็ว่าง จึงกดปุ่ม "▶ เริ่มดำเนินการซ่อม" / "✓ ซ่อมเสร็จ" / อัปเดตความคืบหน้า
เองไม่ได้อยู่แล้ว (เงื่อนไขปุ่มคือ `hasRole('tech')` + `assignedTechs(o).includes(state.myTechName)`)

หน้างานจึงต้องจัดให้ไปคู่กับช่างที่มี LINE เสมอ **คนคู่คือทั้งผู้รับแจ้งเตือนและคนกดปุ่มแทน** —
เป็นเรื่องที่ ผจก.แผนกซ่อมบำรุงจัดเองได้ด้วยตรรกะ **ไม่ต้องมีระบบจับคู่ในโค้ด** และไม่ต้องมีกฎ
มาบังคับว่าห้ามใส่คนที่ไม่มี LINE สองคนไว้ด้วยกัน (ไม่มีใครทำอยู่แล้ว เพราะงานจะเดินไม่ได้)

โค้ดจึงทำแค่สองอย่าง:

* `notifyTech()` **ไม่ใส่ `fallbackRole`** — หา `userId` ไม่เจอก็ข้ามการส่ง LINE ไปเลย ไม่ให้ relay
  ไปไล่หาแถวตามชื่อช่างในชีตแล้วตอบ `sent:0` กลับมา ซึ่งจะทำให้คนกดปุ่มโดน toast
  "ส่ง LINE ไม่ออก" ทุกครั้งทั้งที่เป็นพฤติกรรมที่ตั้งใจ · บันทึกการส่งขึ้นเป็น **⏭️ ข้าม (ตั้งใจ)**
  แยกจาก ❌ ไม่ถึงใคร ชัดเจน
* ดรอปดาวน์เลือกช่างตอนมอบหมายติดป้าย **"— ไม่มี LINE"** ท้ายชื่อ เพราะ ผจก.แผนกซ่อมบำรุง
  จำไม่ได้ว่าใครในแปดคนถูกผูกไว้แล้วบ้าง เห็นป้ายก็จัดคู่เองได้

ถ้าวันหลังผูก LINE ให้เขาแล้ว `lineIdsForPerson()` จะหาเจอเองทันที ไม่ต้องแก้โค้ด

### 4. ใบที่มอบหมายแล้วไม่มีหมุดความคืบหน้าให้กด (แก้แล้ว)

`notifyOpinionStep()` เป็นตัวเดียวที่แจ้งครบทั้ง 3 ฝ่าย (ผู้แจ้ง + ผจก.แผนกซ่อมบำรุง + ช่าง) แต่เดิม
หมุดผูกกับ `maintRecord.inspectorOpinion` อย่างเดียว ส่วน `assignment.executionPlan` ที่เลือกตอน
มอบหมายเป็น **คนละฟิลด์ คนละชุดคีย์** (`need_purchase` ≠ `buy_parts`) ใบที่มอบหมายแล้วเลือก
"ต้องการสั่งซื้ออุปกรณ์" ไว้จึงไม่มีหมุดให้กดสักขั้น และไม่มีใครได้รับแจ้งความคืบหน้าเลย
(`ST-WH005/26` เป็นเคสนี้เป๊ะ) ตอนนี้ `progressTrackOf()` ตกมาใช้ `executionPlan` เมื่อยังไม่มี
บันทึกซ่อมบำรุง

## การแจ้งเตือนที่ระบบส่งในแต่ละสถานะ

| เหตุการณ์ | ใครได้รับ |
|---|---|
| ส่งใบแจ้งซ่อมใหม่ | ผู้จัดการโรงงาน (fm) |
| ผู้จัดการโรงงานอนุมัติ | ผู้จัดการทั่วไป (gm) + **ผู้แจ้งซ่อม** |
| ผู้จัดการโรงงานไม่อนุมัติ / ขอข้อมูลเพิ่ม | ผู้แจ้งซ่อม |
| ผู้จัดการทั่วไปอนุมัติ | ผู้จัดการแผนกซ่อมบำรุง (maint) + **ผู้แจ้งซ่อม** |
| ผู้จัดการทั่วไปไม่อนุมัติ / ขอข้อมูลเพิ่ม | ผู้แจ้งซ่อม |
| ผู้แจ้งซ่อมส่งข้อมูลเพิ่มเติมกลับ | ผู้อนุมัติขั้นที่ค้างอยู่ (fm หรือ gm) |
| มอบหมายช่าง | ผู้แจ้งซ่อม + ช่างที่ถูกมอบหมายรายคน |
| อัปเดตความคืบหน้า (สั่งของ/ของมาส่ง/ส่งซ่อม ฯลฯ) | ผู้แจ้งซ่อม + **ผู้จัดการแผนกซ่อมบำรุง** + ช่างที่ถูกมอบหมายรายคน |
| ช่างเริ่มซ่อม | ผู้แจ้งซ่อม |
| ช่างซ่อมเสร็จ | ผู้แจ้งซ่อม + **ผู้จัดการแผนกซ่อมบำรุง** |
| ผู้แจ้งซ่อมตรวจรับ ผ่าน / ไม่ผ่าน | ผู้จัดการแผนกซ่อมบำรุง + ช่างที่ถูกมอบหมาย |

(ตัวหนา = เพิ่มเข้ามาเมื่อ 3 ก.ย. 2026)

ตั้งแต่ `APP_VERSION 2026-09-04.1` ทุกแถวที่ส่งถึง **ช่าง** จะถูกบันทึกเป็นการแจ้งเตือนในแอปด้วย
(เดิมเป็น LINE ล้วน) ช่างที่ยังไม่ถูกผูก LINE จึงยังเห็นงานของตัวเองที่กระดิ่งได้

## กันไม่ให้เกิดซ้ำ

* `RELAY_VERSION` ใน `docs/line-relay.gs` ต้องเท่ากับ `RELAY_CODE_VERSION` ใน `index.html` เสมอ
  แก้ไฟล์ relay เมื่อไร ให้บั๊มทั้งสองที่พร้อมกัน แล้วแอปจะเตือนเองทันทีถ้าลืม Deploy
* ห้ามสรุปสาเหตุความล้มเหลวจากตัวเลขเดียว (`sent`) อีก — ทุกความล้มเหลวต้องรายงานว่า
  ตกที่ขั้นไหนและรหัสตอบกลับจริงคืออะไร
* **ห้ามวินิจฉัยจากตารางสรุปในหน้าตั้งค่าเพียงอย่างเดียว** ตาราง "ผู้รับแจ้งเตือนที่แอปหาเจอตอนนี้"
  ไล่แค่ `admin/fm/gm/maint` ไม่มี `requester` กับ `tech` และ `state.lineSendLog` อยู่ในหน่วยความจำ
  ของเบราว์เซอร์คนที่กดปุ่มเท่านั้น admin จึงไม่มีวันเห็นความล้มเหลวของคนอื่น — ตัวจริงที่ต้องเปิด
  คือแท็บ **`Relay Log`** (รหัส HTTP รายคน) และแท็บ **`การแจ้งเตือน`** (เทียบกับ `statusHistory`
  ของใบว่าแถวไหนหายไป)
* **ห้ามเขียนคีย์ที่เป็นอาร์เรย์ก้อนเดียวด้วยค่าจากหน่วยความจำตรงๆ** (`notifications`, `accessRequests`,
  `orders`) ต้องดึงของล่าสุดมาเป็นฐานก่อนเสมอ ไม่งั้นเสียข้อมูลของคนอื่นแบบเงียบๆ
